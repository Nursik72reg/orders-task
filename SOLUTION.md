# Решение

## Что сделано

История коммитов повторяет порядок работы: первый коммит — исходный код задания, дальше по одному коммиту на изменение, в каждом — тест и исправление.

| # | Изменение | Где |
|---|---|---|
| 1 | День заказа считается по смещению таймзоны на момент заказа, а не запроса | `src/services/totals.ts`, `src/utils/time.ts` (`localDate`) |
| 2 | Версия заказа применяется атомарно: один условный upsert вместо «прочитать, потом записать» | `src/repositories/orders.ts` (`saveIfNewer`), `src/services/orders.ts` |
| 3 | Рубли переводятся в копейки по десятичной записи числа, без умножения float | `src/utils/money.ts` (`toKop`) |
| 4 | Скидки: `gross`, `discount`, `net` в `daily-totals` | миграция `002`, `src/services/orders.ts`, `src/services/totals.ts` |

`result.json` — ответ `daily-totals` для `c_7` за 27–31.03.2026, получен по процедуре из `TASK.md`.

### Принятые решения

- **`net` берётся из `amountPaid`**, а не пересчитывается из процента: это то, что клиент заплатил фактически, и именно с этим числом сверяется платёжная система. `discount` считается как `gross - net` в копейках, в рубли переводится только итог.
- **Храним только оплаченную сумму** (`orders.amount_paid_kop`), процент скидки не храним: для статистики он не нужен, а два источника одной величины могут разойтись.
- **`amount_paid_kop` допускает NULL** — «сумма неизвестна». Это отличается от «скидки нет»: у заказов до 15.03 полей скидки во внешнем API нет вообще.
- **Группировка по дням осталась в коде, а не в SQL.** Исправление минимальное и проверяется юнит-тестами без БД. Вариант с `GROUP BY (created_at AT TIME ZONE tz)::date` масштабируется лучше — см. «Что бы доделал».
- **Невалидные поля скидки делают заказ невалидным** (вебхук — 400, в синке — счётчик `invalid`), как и невалидная сумма: молча считать такой заказ без скидки значило бы тихо исказить `net`.
- **Существующие тесты `daily-totals` дополнены новыми полями.** Они сравнивали ответ целиком (`toEqual`), поэтому с новыми полями пройти без правки не могли. Значения `total` в них не менялись.

## Причина расхождения из жалобы

**Причина.** `TotalsService.daily` брал смещение таймзоны клиента один раз — на момент запроса (`tzOffsetMinutes(timezone, new Date())`) — и применял его ко всем заказам периода. Клиент `c_7` живёт в `Europe/Berlin`, где 29.03.2026 переход на летнее время: до него смещение +1 ч, после — +2 ч. При запросе зимой ко всем заказам применялось +1, и заказы, созданные между 22:00 и 23:00 UTC начиная с 29.03, попадали в предыдущий день. Поэтому 27 и 28 марта сходились до копейки, а 29, 30 и 31 — нет. Баг зависит от даты запроса: летом расходились бы, наоборот, дни до перехода.

Баг не специфичен для `c_7`: он затрагивает любого клиента в таймзоне с переходом на летнее время (в данных это ещё `Europe/London` и `America/New_York`), если у него есть заказы в час около полуночи. Исправление общее.

**Как нашёл.**
1. Прочитал код расчёта и заметил, что смещение не зависит от времени заказа.
2. Запросил таймзону `c_7` во внешнем API — `Europe/Berlin`, переход 29.03 попадает ровно в период из жалобы.
3. Выгрузил все заказы из внешнего API и посчитал суммы по дням отдельным скриптом двумя способами: с правильной таймзоной и с постоянным смещением +1 ч. Запустил неизменённый сервис — его ответ совпал со вторым вариантом до рубля, расходились именно 29, 30 и 31 марта.
4. Написал тест с заказами по обе стороны перехода (он падает при любом постоянном смещении), затем исправил.

**Вторая причина, найденная по ходу.** После вебхуков сумма за 29.03 в неизменённом сервисе менялась от запуска к запуску: в 3 прогонах из 4 она была завышена на 3675 ₽. Внешняя система шлёт вебхуки параллельно (до 6 одновременно), с повторами и не по порядку, а `OrdersService.apply` сначала читал заказ, потом писал. Устаревшая версия `paid` заказа `o_02281` затирала более свежую `refunded`. Исправлено коммитом 2; без этого `result.json` получался бы верным только при удачном порядке доставки.

## Как проверял результат

- **Тесты.** `npm test` — 49 тестов (было 27), `npm run typecheck` чистый. Для каждого исправления сначала написан тест и проверено, что он падает по ожидаемой причине.
- **Независимый эталон.** Отдельный скрипт, не использующий код сервиса, считает суммы по `c_7` из сырых данных: выгрузка `/orders` плюс перехваченные вебхуки, последняя версия заказа по `updatedAt`, копейки — целочисленно из строкового представления, день — через `Intl` в `Europe/Berlin`. `result.json` совпал с ним до копейки.
- **Повторяемость.** Полная процедура из `TASK.md` (чистая БД → синк → вебхуки → запрос) выполнена 3 раза подряд — ответ побайтно одинаковый. Поток вебхуков перехватывался 3 раза: содержимое одинаковое (92 вебхука, 37 уникальных версий по 21 заказу), меняется только порядок.
- **Перекрёстная проверка по всем клиентам.** Ответ сервиса по всем 40 клиентам за 27.02–02.05 (2600 дней, из них 1738 с оплатами) сверен с расчётом прямо в PostgreSQL — другая реализация таймзон, другой код суммирования. Расхождений нет:

  ```sql
  SELECT (created_at AT TIME ZONE '<таймзона клиента>')::date, sum(amount_kop), sum(coalesce(amount_paid_kop, amount_kop))
    FROM orders WHERE customer_id = '<id>' AND status = 'paid' GROUP BY 1;
  ```

- **Сверка «до и после».** Ответ неизменённого сервиса сохранён и объяснён: каждое отличие от итогового результата соответствует конкретному заказу и конкретной причине (смещение таймзоны либо затёртый возврат).

Замечание об окружении: у меня Docker работает внутри виртуальной машины, и `host.docker.internal` из контейнера не ведёт на хост. Вебхуки запускал той же командой из `README.md`, но с адресом `http://host.lima.internal:3000/webhooks/order`. На содержимое вебхуков это не влияет.

## Что ещё заметил

### В коде

- **Потеря копейки в `toKop`** (исправлено). `Math.floor(rub * 100)` даёт `230546` для `2305.47`. На суммах `amount` в текущих данных не проявлялось (они целые), но для `amountPaid` это 96 заказов из 5030, из них 6 — в окне из задания: без исправления `net` врал бы на 1–2 копейки в 4 днях из 5.
- **Повторный синк не обновил бы уже сохранённые заказы** (исправлено). После миграции у старых строк оплаченная сумма неизвестна, а синк отдаёт их с тем же `updatedAt` — раньше такая версия считалась устаревшей. Теперь та же версия дозаполняет оплаченную сумму.
- **Синк целиком падает, если одна страница не получена после всех попыток**; продолжить с места остановки нельзя. Заказы пишутся по одному запросу на заказ.
- **`POST /sync` синхронный** — запрос висит до конца прохода. Защита от параллельного запуска хранится в памяти процесса и не работает при нескольких экземплярах сервиса.
- **Клиент внешнего API считает ограничением частоты любой ответ 200 с полем `error`.** Сейчас это верно, но другая ошибка в таком виде будет бессмысленно повторяться все 8 попыток.
- **Таймзона клиента кешируется навсегда** — если она изменится во внешней системе, сервис об этом не узнает.
- **У `daily-totals` нет ограничения на длину периода**, а расчёт загружает в память все заказы периода.
- **Вебхуки принимаются без проверки подлинности** (подписи или секрета нет).
- **Две версии с одинаковым `updatedAt`, но разным содержимым** неразличимы: вторая считается повтором. В текущих данных таких нет.

### В поведении внешнего API

- **Ограничение частоты срабатывает и ниже заявленных 5 rps**: при ~4 запросах в секунду изредка (3 раза на 55 запросов) приходит `200 { "error": "rate_limited" }`. При превышении — 429, заголовок `Retry-After` есть не всегда.
- **Формат данных нестабилен:** `createdAt` без указателя зоны — 288 заказов (проверил по соседним заказам в списке: это действительно UTC); `amount` строкой — 157; `discountPercent` строкой — 177; полей скидки нет вовсе — 1177 заказов (все созданы до 15.03).
- **`amountPaid` всегда согласован с `amount` и `discountPercent`** с точностью до копейки — противоречий в данных нет.
- **Пагинация по смещению.** Курсор — это закодированное смещение (`o:100`), список не отсортирован по `createdAt` (в хвосте 30 заказов «задним числом»), конец списка обозначается пустой страницей с тем же курсором, а не `nextCursor: null`. Если заказы добавятся во время синка, возможны пропуски и повторы.
- **Вебхуки:** все 92 — по клиенту `c_7`, 55 из них — точные повторы; приходят параллельно и не по порядку; меняют не только статус, но и скидку. Снимок в `/orders` старше версий из вебхуков.
- **Ошибки запроса** (`limit` больше 100, неверный курсор) — 400 с телом `{ "error": "<код>" }`; неизвестный клиент — 404.

## Допущения

- **Заказ относится ко дню создания (`createdAt`)**, как и раньше. В API нет времени оплаты, и расчёт по `createdAt` совпал с ожиданием аналитиков по «хорошим» дням.
- **Заказ без полей скидки считается оплаченным полностью** (`net = gross`, `discount = 0`). На `result.json` не влияет: в окне задания у всех заказов поля есть.
- **Если `amountPaid` нет, а `discountPercent` есть** — оплаченная сумма считается по проценту с округлением до ближайшей копейки. В данных такого случая нет, правило округления выбрано мной.
- **`amountPaid` больше `amount` или процент вне 0–100 — заказ невалиден.** Отрицательная скидка противоречит описанию поля в `README.md`.
- **Возвраты и неоплаченные заказы не входят ни в одну из сумм** — как и раньше для `total`.
- **Из двух версий заказа побеждает та, у которой больше `updatedAt`**, независимо от порядка доставки и источника (синк или вебхук).
- **`result.json` — ответ сервиса как есть**, без форматирования.

## Что бы доделал при наличии времени

- Перенёс бы группировку по дням в SQL (`AT TIME ZONE`) с агрегацией в базе и ограничил бы длину периода в запросе.
- Сделал бы синк возобновляемым: сохранять курсор в `sync_runs`, писать заказы пачками, вынести проход в фоновую задачу с блокировкой в БД вместо флага в памяти.
- Различал бы в клиенте внешнего API ограничение частоты и прочие ошибки с кодом 200; добавил бы случайную добавку к паузам между попытками.
- Добавил бы проверку подлинности вебхуков и журнал отклонённых событий — сейчас невалидные заказы только считаются, но не сохраняются для разбора.
- Обновлял бы таймзону клиента по сроку давности, а не хранил вечно.
- Договорился бы с командой внешнего API о версии заказа (номер вместо `updatedAt`), едином формате полей и курсоре, устойчивом к вставкам.
- Добавил бы линтер, запуск тестов в CI и тест клиента внешнего API на поведение при 429 и `rate_limited`.
